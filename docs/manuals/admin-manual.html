The two-minute version

Three protocols. Everything after them is the detail behind these.

Protocol A — add a user

Supabase dashboard, once per person:

  1. Authentication → Users → Add user → Create new user

  2. Their email, and a password you invent — write it down.

  3. Tick “Auto Confirm User.” Skip it and they cannot sign in at all.

  4. Create user

Office app, right after:

  1. Settings → Users → Refresh

  2. They appear as: name = their email, role = crew, status = not active

  3. Type their real name over the email, then click away.

  4. Set the role in the dropdown.

  5. Click Activate.

  6. Text them the app URL, their email, and the password.

Protocol B — edit a user

All in the app, Settings → Users.

To do thisDo this
Fix a nameType over it, click away
Change roleDropdown → confirm
Remove accessDeactivate — instant, everywhere, history kept
Restore accessActivate

Your own row and the last active owner’s row are locked. That is the lockout guard, not a fault.

Protocol C — someone cannot get in and has no history

For an account created but never used, where nobody knows the password.

Only safe when the person has no history in the books. Otherwise deactivate them and start a fresh account instead — deleting a user with history fails on a foreign key (section 6).

  1. Authentication → Users → find them → Delete user

  2. Add user → Create new user — same email, a password you choose, Auto Confirm ✓

  3. App → Settings → Users → Refresh → name → role → Activate

  4. Text them the URL, email, and password.

There is no emailed password reset available today. Supabase refuses to deliver auth mail to any address outside the project’s organization until a custom SMTP server is configured — a refusal, not a rate limit. That is open item 1; until it is done, you are the reset mechanism.

01

The three roles

The database allows exactly three role values. A CHECK constraint on user_profiles.role rejects anything else.

RoleWhoIn one line
ownerJohn Everything, including hard deletes and the money screens.
officeBookkeeper, office help Runs the books day to day. No hard deletes on core records.
crewCowboys Read-only. Can look at the books but change nothing, and cannot see invoices at all.

On naming. The roadmap called these admin / manager / cowboy / guest. What shipped is owner / office / crew, and there is no guest role. Use the shipped names — the constraint and every policy are written against them.

Roles are flat, not inherited. Each policy names the roles it allows. But because every write policy is either owner + office or owner alone, write access happens to form a clean ladder, and the app's role gate depends on that.

02

How it actually works

Three moving parts. Understand these and the rest is mechanical.

The profile table

One row per person, keyed to their auth.users id. The columns that matter are role, and is_active — the on/off switch.

The function every policy calls

Two consequences worth holding on to:

  • is_active = false returns NULL, and NULL = ANY (...) is never true. An inactive user is denied by every policy on every table. Deactivating is a complete, instant kill switch.
  • A signed-out visitor has no auth.uid(), so they get NULL too. Some policies target the public Postgres role rather than authenticated — cosmetically inconsistent, but not a hole, because the NULL check closes it either way.

The signup trigger

on_auth_user_created fires on every insert into auth.users and creates the profile with:

  • role = 'crew' — hardcoded. The role is never read from signup metadata, so nobody can promote themselves by crafting a signup.
  • is_active = false — this is the gate. A new account can sign in but can read and write nothing until you activate it.

There is no INSERT policy on user_profiles. The trigger is the only way a profile row appears, and only an owner can update one.

03

Adding a user

Two steps: create the login in the Supabase dashboard, then finish them off in Settings → Users in the app. Only the first needs the dashboard.

Open the project dashboard →

The Users screen

Settings → Users, visible to owner only. The sub-tab is hidden from everyone else by the role gate, and the roster function returns zero rows to anyone who is not an active owner — so it fails closed even if someone reaches the tab.

It lists everyone with name, email, role, status, and last sign-in:

  • Rename — type over the name and tab away. New accounts arrive with their email address as a placeholder name, so this is usually the first fix.
  • Change role — the dropdown, with a confirm.
  • Activate or deactivate — the button on the right.

Two rows are deliberately locked: your own, so you cannot demote or deactivate yourself by accident, and the last active owner. The database refuses both anyway through a trigger; the screen simply does not offer them.

Creating the login itself stays in the dashboard. A browser cannot create an auth.users row, and the key that could must never ship inside a client-side app. That is once per person, and rare.

  1. Create the login

    Authentication → Users → Add user. Two ways:

    Send invitation — they get an email and set their own password. Best for office staff.

    Create new user — you set the password and hand it over. Best for cowboys, who may not have easy email access on a horse. Tick Auto Confirm User, or they cannot sign in until they click a link.

    The trigger now creates their profile: crew, inactive, name defaulted to their email address because the dashboard form has no name field. They can do nothing yet. That is correct.

  2. Set the name, role, and activate

    In the app: Settings → Users. Type over the placeholder name, set the role, click Activate. Done.

  3. Verify before handing over the password

    You want is_active and confirmed both true. If confirmed is false they will hit "Email not confirmed" at sign-in — go back to Authentication → Users, open them, and confirm.

What each role can do

The database is the enforcement. The app hides controls a role cannot use, but that is presentation only. Anyone who gets past the interface still hits the policies, and the policies are what actually refuse them.

Reads

All three roles read everything except invoices and invoice_attachments, which are owner and office only. That is the one hard wall in the schema, and the only place a role is denied SELECT.

05

Changing a role

Settings → Users, change the dropdown. Or by SQL:

It takes effect on their next request — current_user_role() is read fresh on every policy check, so there is no need to make them sign out. Their header badge stays stale until they reload; their actual permissions are already current.

Keep at least one active owner. Nothing stops you demoting yourself and locking everyone out of user administration. If it happens, the SQL Editor still works — it bypasses RLS — and can put it back.

06

Removing someone

Deactivate — the right answer

Settings → Users, click Deactivate. Or by SQL:

Immediate and total on two levels: current_user_role() goes NULL so every policy denies them, and the login screen refuses them by name rather than letting them into an empty app. Anyone already signed in is kicked out the next time it loads. Their history stays intact and attributed.

Reactivating is the same statement with TRUE.

Do not delete auth users

Most of the books point at auth.users with ON DELETE NO ACTION. Anyone who has ever created a lot, sale, receipt, invoice, weight, movement, pasture assignment, ranch, pasture, medication, or protocol cannot be deleted — the delete fails on a foreign key violation.

A few columns are ON DELETE SET NULL (doctoring_events.recorded_by_user_id, lot_tags.registered_by, the attachment uploaded_by columns). Those would quietly lose their attribution — you would erase who doctored what.

Both outcomes are bad. Deactivate, never delete.

Verifying a role works

Do not trust the table in section 4 — test it. Sign in as the user in a private browser window and confirm both halves.

Sign in asWhat you should see
crew Lots and tags visible. No add, edit, or delete buttons anywhere, and no Invoices card on a lot. Reading works; nothing else does.
office Can record a sale and edit a lot. The owner-only controls are absent — "Delete all test lots" in Settings, and Delete invoice on an open invoice.
owner Everything, including both of the above.
An inactive account Bounced at the login screen with "Your account is not active yet." Never reaches the app.

What only you can do

The migration, and two settings nothing but the dashboard can reach.

Run the Users screen migration

docs/sql/2026-08-24_users_admin.sql adds two things the screen needs: admin_list_users(), the owner-guarded roster — necessary because authenticated has no SELECT on auth.users and PostgREST only exposes the public schema — and guard_last_owner(), a trigger that refuses to let the final active owner be demoted or deactivated.

SQL Editor, paste, Run. It verifies its own grants and raises if anon can still execute the function.

The full list of what is still open — including the missing email provider — lives in docs/OPEN-ITEMS.md in the repo.

Leaked-password protection

Authentication → Policies (password settings) → enable it. Supabase then checks new passwords against HaveIBeenPwned and rejects known-breached ones. Do this before handing out passwords.

Public signup

Authentication → Sign In / Providers → check whether "Allow new users to sign up" is on. If it is, anyone with the app's URL can create an account. They land as inactive crew and can do nothing, so this is not a breach — but it lets strangers put rows in your auth table. Turn it off and add people by invitation, per section 3.
